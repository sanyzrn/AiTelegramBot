Received `NexaHR_11_review_prompts.md` and executed **PROMPT 01 — Authz & Session** (`Mode: defects + elevation`) against the local `main` checkout.

## Verdict — 3 lines

The two-axis model (role vs capability), JWT `token_version` revocation, session rotation, and row-level evaluation scoping are implemented carefully and mostly match their comments.
The serious gap I executed is not in JWT itself: Excel personnel import can return HTTP 200 while silently creating no evaluation chain when the CEO column is empty and more than one active CEO exists — the same “uncaseable person” failure the chain columns were added to prevent.
Secondary authz gap: `POST /api/auth/change-password` rate-limits per IP but never locks the account, so a stolen access token can brute-force the current password across IPs.

## Findings — severity | file:line | what breaks | how to reach it | fix

**High | `backend/app/services/personnel_import.py:232-240`, `416-417`, `601-610` | Import reports success but creates no evaluation chain |** HR (`manage_personnel` or `hr`) posts a valid xlsx to `/api/personnel/import` with «معاونت مربوطه» filled and «مدیرعامل» empty (the common case the sole-CEO auto-fill is for). Org has ≥2 active CEO users (demo leftover `ceo1` + real CEO, or two living CEOs). `sole_ceo=None` → `ceo_user_id` stays `None` → `has_chain` is false → `commit_import` inserts Personnel only, `created_chains=0`, `skipped_rows=0`, no `EvaluationAccess`. Person sits with no scorer and no closer. **Verified** by executing the flow against `nexahr_test`. **Fix:** after `sole_ceo` resolution, if any chain column was partially provided and `ceo_user_id` is still `None`, mark the row invalid («ستون مدیرعامل خالی است و بیش از یک مدیرعامل فعال هست»); never treat `has_chain=False` on a partial chain as success.

**Medium | `backend/app/api/routers/auth.py:240-286` + `services/login_guard.py` | Account takeover via unlimited current-password guessing |** Attacker with a valid access token (XSS, shared machine, stolen laptop session) POSTs `/api/auth/change-password` with wrong `current_password`. Only `@limiter.limit("10/minute")` applies (per-IP, in-process). `login_guard.record_failure` is never called; rotating IPs bypasses the limiter entirely; there is no lockout on this path. Success permanently changes the password and bumps `token_version` (full lockout of the victim). **Verified** by reading both paths; lockout tests cover `/login` only. **Fix:** on wrong `current_password`, call `record_failure(db, user.username)` and refuse while `locked_until` is in the future; clear failures on success. Keep the existing 10/min rate limit.

**Medium | `backend/app/services/authorization.py:63-71` + `backend/app/api/routers/users.py:249-289` | Promoting an account to `hr` wipes all capabilities, including `manage_capabilities` |** Bootstrap admin is `support` with every capability. The self-update guard only blocks *leaving* `hr` (`updates["role"] != UserRole.hr`); `support → hr` is allowed. That branch calls `apply_default_hr_capabilities`, which **deletes every row** then inserts only `DEFAULT_HR_CAPABILITIES` (no `manage_capabilities`). If that user was the last capability admin, `has_active_admin` becomes false and nobody can grant capabilities until process restart recreates bootstrap admin. **Verified** by reading the wipe + the self-role guard; not executed end-to-end. **Fix:** merge into defaults instead of delete-all, or preserve `manage_capabilities` when the actor is the sole holder; also refuse non-HR → HR self-mutation unless a second capability admin exists.

## Verified correct

- **Forced password change:** server-side allowlist (`change-password`, `me`, `my-permissions`) blocks the rest of the API; tests cover blocked/unblocked paths.
- **Refresh cookies:** HttpOnly, `SameSite=strict`, `path=/api/auth`; rotation uses `FOR UPDATE` + `populate_existing`; reuse outside grace revokes the whole family (`sessions.py:103-125`).

## Proposals

1. **HR can tell why an import “worked” but the person is not in any queue** — After import, the result lists counts only (`created_personnel` / `created_chains`). Add per-row outcome in preview and commit (`chain: complete | incomplete_ceo | incomplete_scorer | none`) and a dashboard filter “no evaluation access”. Change: `personnel_import.py` ImportRow/preview schema + import UI table + optional personnel list filter. Files: ~3–4. Breaks: nothing legal; already-finalized records untouched.

2. **Change-password lockout uses the same username counter as login** — (Implementation of Finding 2; listed as the product outcome:) a stolen session cannot grind current-password guesses off-IP. Files: `auth.py` + tests. Breaks: none; failed attempts already appear in `login_attempts`.

3. **Import refuses partial chains instead of silently dropping them** — (Implementation of Finding 1.) Preview already shows errors; commit must not accept a row that had chain columns but no closer. Files: `personnel_import.py` + import tests. Breaks: files that intentionally omit all three chain columns still import as personnel-only; files that omit only CEO no longer “succeed” without a chain.

4. **Capability wipe on role→HR should not lock out the last capability admin** — (Implementation of Finding 3.) Outcome: system remains administrable after HR promotion. Files: `authorization.py` + `users.py`. Breaks: none for already-finalized documents; new HR accounts still get the documented baseline *in addition to* preserved admin caps when sole-holder rule applies.

5. **Separation banner counts only *chosen* separation, not migration leftovers** — `/api/administration/separation` is correct but noisy on day-one HR. Outcome: HR sees “default baseline still on N HR accounts; move rule-changing caps to support” as an action list, not just `separated: false`. Files: `administration.py` + admin UI copy. Breaks: none; no data migration.

6. **Forced-password and lockout events stay on one HR security feed** — Lockout already notifies HR; password-reset and capability wipe do not. Outcome: one `/hr/audit-log` view answers “who lost access / who gained power today”. Files: `audit_events` already has most labels; add notify_once on capability wipe and sole-admin lockout risk. Breaks: none; notification volume only if un-deduped — keep `notify_once`.
