## Verified correct
- **Migration replay from empty** — `alembic upgrade head` on a fresh database: all 63 migrations apply cleanly in ~1.4 s, head `f1b6d3e28a47`; the resulting schema is what 1542 green tests run on.
- **Model/schema drift** — `alembic.autogenerate.compare_metadata` against the live migrated DB: empty diff (no missing/extra tables, columns, indexes, or type changes).
- **Enums both directions** — 12 enum types in `pg_type` (`user_role`, `evaluation_status`, `personnel_status`, `period_status`, `scheme_status`, `delivery_status`, `delivery_channel`, `capability`, `comment_stage`, `improvement_plan_status`, `indicator_section`, `separation_reason`) match `app/models/enums.py` value-for-value, no Python-only DB values and no DB-only Python values. `EvaluationStage` (`models/enums.py:44`) exists only to derive a display stage from `EvaluationStatus` in `schemas/evaluation.py:20` and is never a column type.
- **Partial unique indexes vs code assumptions** (the prompt's rule-4 pair):
  - `uq_open_evaluation_per_personnel` (evaluation_records, `WHERE status <> ALL(finalized, cancelled)`) — equivalent to `OPEN_STATUSES` **today**, because the enum has exactly six values; both sides enumerate the same closed set from opposite directions (row filter in `models/evaluation.py:289`, frozenset in `services/workflow.py:34`). Caveat for the owner, not a defect: if a seventh **terminal** status is ever added to the enum, `OPEN_STATUSES` and this index must both be touched or the index will treat the new terminal status as "open" and wrongly enforce one-record-per-person against it. The pair is comment-locked in `services/privacy.py:31`.
  - `uq_single_open_period` (evaluation_periods, `WHERE status='open'`) — matches the singleton-open assumption at `routers/periods.py:65,77,248` and `services/bulk_evaluation.py:243`.
  - `uq_single_active_scheme` (scoring_schemes, `WHERE status='active'`) — matches `services/scoring_scheme.py:89` (singleton lookup) and `:204` (activation).
- **Append-only audit table** (executed): `UPDATE audit_log …` → blocked (`InsufficientPrivilege: audit_log is append-only: UPDATE is not permitted`); `DELETE …` → blocked the same way (my first probe *appeared* to delete — it was a no-row DELETE on an empty table, a probe artifact, not a bypass; with a row present the trigger fires); `TRUNCATE` → blocked; `INSERT` with NULL hash columns → blocked by NOT NULL. Triggers: `trg_audit_log_append_only` (row-level UPDATE/DELETE) + `trg_audit_log_no_truncate` (statement-level TRUNCATE), migration `e8f4b127d905`.
- **Hash chain logic** (`services/audit.py`) — `_canonical` sorts keys and excludes `created_at` (server-assigned at INSERT; the trigger, not the hash, protects it — the exclusion is documented at `audit.py:54`); `log_event` serializes concurrent appends on `pg_advisory_xact_lock(:key)` before reading the tail (`audit.py:87`), so the chain cannot fork (a separate concurrency agent's 8×25 parallel-write probe ended `verify_chain ok=True, checked=200`); `verify_chain`'s three modes (full / tail-window / since-anchor) all share `_walk`, the anchor is re-verified against the log row before use (`audit.py:188`), and `record_full_verification` is the only place the anchor advances and only after a fully successful walk (`audit.py:280-330`) — the "fast green" blind spot is correctly closed.
- **Cascades / orphans on delete** — `delete_user` (`routers/users.py:353`) refuses any account with audit history (409, with the reason), cleans its direct dependents, and wraps the final delete in `except IntegrityError` so the *database*, not a code-maintained list, is the source of truth for "is this account referenced"; `audit_log.actor_user_id` is deliberately RESTRICT (an actor is never hard-deleted — enforced, and my probe confirmed the FK blocks it); AI tables use CASCADE/SET NULL correctly (`ai_user_access`, `ai_conversations`/`ai_messages` CASCADE; `ai_usage_log` SET NULL); `delete_org_unit` refuses units with personnel (string-count guard, `org_units.py:175`); `org_unit` on `personnel` is a deliberate free-string (owned by the docstring at `models/org_unit.py:5-16`) and the rename endpoint moves all matching personnel rows in one UPDATE (`org_units.py:138-144`) — a test-quality agent separately verified that cascade is untested (their finding, not a data-integrity break).
- **String-vs-enum comparisons** — every `status`/`role` comparison in `app/` is typed against an enum member (sweep across routers/services); the only raw-string status comparisons live on genuine `VARCHAR` columns whose written values match exactly: `SchedulerRun.status` (writes `skipped_locked/running/succeeded/failed` at `services/scheduler_lock.py:65-84`; compares `admin.py:33`, `readiness.py:60`), `AiPendingAction.status` (writes `pending/executing/confirmed/failed/expired/rejected` at `services/ai/confirmations.py:55-216, orchestrator.py:259`; compares the same strings, always conjunct with the row id), `AiMessage.role == "assistant"` (`api/routers/ai.py:293`).

## Could not check, and why
- **Alembic downgrade paths** — the prompt asks for replay from empty, not round-trip; downgrade of all 63 migrations was not exercised (nothing in the product's workflows downgrades; risk accepted).
- **Tamper-proofness of the audit trail** — by the design's own admission (`audit.py:14-20`): this deployment has a single DB role, so the role that *owns* the table can `ALTER TABLE … DISABLE TRIGGER` it — I executed exactly that successfully as the app role (and re-enabled it). The hash chain makes tampering *detectable* only if the verifier's anchor is out of the attacker's reach; a party holding both DB and code can rebuild the chain. The docstring names the missing piece (an external append-only sink) as an undecided infrastructure item. Design objection, not a bug: worth deciding, not fixing in code.
- **`ix_evaluation_records_open_objection`** — a non-unique partial index (`WHERE objection_at IS NOT NULL AND objection_resolved_at IS NULL`, migration-built) with **no consumer query anywhere** in `app/` or the frontend: objections are resolved per-record by id, and no list/queue/dashboard filters on open objections. Nothing fails (rule 5) — it is dead weight on writes today, or scaffolding for an objection queue that does not exist yet. The owner should either delete it or build the queue it anticipates.
- Historical migration-by-migration enum-value evolution (each intermediate state) — the final state is proven consistent by the live diff; replaying 63 intermediate states individually would add evidence about *transitions*, not about what runs today.
