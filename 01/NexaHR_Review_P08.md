# P08 — Localization review (core/clock.py, UTC/local boundary, Jalali/PDF, Persian digits, RTL CSS, labels)

## Verdict — 3 lines
The UTC/local boundary is genuinely owned by `core/clock.py`: every timestamptz range filter goes through `local_day_start`/`local_day_end`, the PDF's Jalali conversion converts through `to_local` first, and the Vazirmatn/Vazirmatn-Latin font pair covers every character the document can emit (verified per-codepoint with fontTools). No regressions of the ALREADY-FIXED list were found. Two real defects remain, both at *input* boundaries the fixed machinery trusts: the manual personnel path accepts Persian-digit codes verbatim (import normalizes, manual does not — duplicate identity risk), and the frontend's "today" helpers use browser-local components instead of the ORG_TIMEZONE they sit next to, so filter presets and the deadline banner disagree with the server around Tehran midnight for any non-Tehran browser.

## Findings — severity | file:line | what breaks | how to reach it | fix

**1. Medium | backend/app/schemas/personnel.py:12 (+ personnel.py:379,656,76-79; contrast personnel_import.py:105,151) — Persian-digit personnel codes accepted verbatim on the manual path**
- What breaks: `personnel_code: str = Field(min_length=1, max_length=50)` has no pattern and no digit normalization, so «۱۲۳۴» and `1234` are two distinct identities to the DB, while the Excel-import path normalizes both to ASCII (`_DIGITS` translate, personnel_import.py:105, applied at :151). Consequences: the duplicate check (`api/routers/personnel.py:379` create, `:656` update, raw `==` on the code) misses the ASCII twin → the same person can exist twice, and each copy can hold its own open evaluation (the one-open-evaluation index is per personnel row); code search (`personnel.py:76-79` `ilike` on the raw string) cannot find «۱۲۳۴» when HR types `1234` (or vice versa), so contract-expiry and evaluation workflows silently skip that person.
- How to reach it: HR creates a person with a Persian keyboard and types/pastes «۱۲۳۴» as the code (verified executed: `PersonnelCreate(personnel_code="۱۲۳۴", …)` validates and stores `«۱۲۳۴»` verbatim). First visible symptom is earlier still: `suggestUsername(form.personnel_code)` (frontend PersonnelPage.tsx:410) feeds Persian digits into the suggested username, and `UserCreate`'s pattern `^[a-zA-Z0-9._-]{3,50}$` (schemas/personnel.py:33) rejects it — HR gets an account-creation validation error for a "valid" code. Later search/import of the same code as `1234` produces the duplicate identity above.
- Fix: normalize Persian (۰-۹) and Arabic-Indic (٠-٩) digits to ASCII at the PersonnelCreate/PersonnelUpdate boundary — or in the router just before the duplicate check — reusing `personnel_import._DIGITS` so both doors to the unique key agree.

**2. Low | frontend/src/utils/dates.ts:50-61 (+ SubmissionDeadlineBar.tsx:41-45, jalali.ts:197-200) — frontend "today" uses browser-local components, not ORG_TIMEZONE**
- What breaks: `localTodayIso()` builds `YYYY-MM-DD` from `getFullYear()/getMonth()/getDate()` — the *viewer's* timezone — although the same file defines and uses `ORG_TIMEZONE` for display (dates.ts:16,19-27). The backend measures every window with `today_local()` (Asia/Tehran, evaluation_window.py:57, scheduled.py:51,78, dashboard.py:484). Whenever the browser TZ ≠ Asia/Tehran, the two sides answer differently for part of every day. Affected call sites: contract-filter presets (`ReportsSection.tsx:260-261,271`, `AuditLogPage.tsx:264-265,275` — "منقضی‌شده"/"N روز" ranges shift by a day) and the submission-deadline banner (`SubmissionDeadlineBar.tsx:45`, which keeps its own second copy of the same logic).
- How to reach it (executed): froze the clock at `2026-01-05T21:30:00Z` (= Tehran 2026-01-06 01:00) with `TZ=UTC`: `localTodayIso()` → `2026-01-05` while the org day is `2026-01-06`; with `closes_on = 2026-01-05`, the bar shows «مهلت ثبت» (open) because `todayKey > deadline` is false, while the backend rule `today_local() <= closes_on` is closed — the evaluator types a self-assessment and gets a 400 on submit. Browsers east of Tehran (e.g. UTC+8) get the inverse for ~8.5h: banner says «مهلت ثبت گذشته است» while submissions still succeed. `jalali.ts:197-200 todayJalali()` has the same bug with visual-only impact (wrong "today" highlighted in JalaliDatePicker).
- Fix: derive the org day once in dates.ts via `Intl.DateTimeFormat("en-CA", { timeZone: ORG_TIMEZONE })` (the module already imports ORG_TIMEZONE for the formatters), use it in `localTodayIso`, delete SubmissionDeadlineBar's inline copy, and build `todayJalali()` from it.

## Verified correct
- **clock.py owns the boundary as claimed.** `to_local` treats naive datetimes as UTC (the storage convention, clock.py:45-54); `org_timezone()` fails loudly on a bad name instead of silently falling back (clock.py:37-42); `local_day_start/end` verified by execution: `local_day_start(2025-10-15) = 2025-10-14T20:30Z`, `local_day_end = 2025-10-15T20:30Z` (+03:30, no DST since 2022). No `date.today()`, `utcnow`, or naive `datetime.now()` anywhere in `app/` (only the demo seed script and tests).
- **Every timestamptz range filter goes through the local boundary:** evaluations.py:559-563, audit_log.py:104-107, reports.py:68-70 and 304-306, ai/tools/analytics.py:259-264, ai.py:749-751. The only `func.date()` in the app wraps `func.timezone(org_timezone, created_at)` first (ai.py:771) — correct local-day grouping. Date-only columns (contract_end_date, review_date, closes_on, period starts/ends) are compared against `today_local()`-derived dates with no zone conversion — correct, since `Date` columns carry no zone (audit_log.py:133, dashboard.py:484-508, analytics.py:405, scheduled.py:51,402).
- **Jalali in the PDF is day-correct.** `to_jalali` converts through `to_local` before `fromgregorian` (pdf.py:35); executed: `2025-10-06T21:30Z → «۱۴۰۴/۰۷/۱۵ ساعت ۰۱:۰۰»` — the exact off-by-one-day scenario the docstring describes, now right. Invalid/old snapshot strings pass through unchanged instead of crashing (pdf.py:28-31, verified `not-a-date` → passthrough). `fa_date` (core/persian.py:48-60) does the same for notification/error text. Excel renders every datetime/date column Jalali (excel.py:200-201,305,330,399,402).
- **Font loading and coverage.** Template declares both families with explicit files (evaluation_summary.html:31-52); all four woff2 files + LICENSE exist in app/templates/fonts; verified with fontTools that the Arabic subset covers Persian letters, ٪ (U+066A), ٫ (U+066B), ZWNJ, and the Latin subset covers ASCII digits, `+ - / : . = ? & _ ~`, «» and — (U+2014) — i.e., no character the template/fa_digits can emit falls through to Tahoma/DejaVu; `_local_templates_only_url_fetcher` keeps external fetching closed (pdf.py:86-94).
- **Persian digits at output boundaries.** `fa_digits` used in all server-authored text (scheduled.py:82-84,164,317-325,425-427,490; notifications.py:250,310,372; me.py:402; evaluation_window.py:105; evaluations.py:1338,1373; tools/uploads.py:228-230); identifiers deliberately stay Latin (persian.py:36-39) and that policy is applied consistently (evaluation_code/personnel_code raw in PDF, Excel, messages). Decimal point → U+066B, None → «—» not «None». Input side: Excel import normalizes Persian/Arabic digits and strips invisible characters except ZWNJ, with the reason documented (personnel_import.py:105-149). Frontend numerals are uniformly Persian (`fa-IR` Intl in dates.ts:19-27, `toPersianDigits`, `formatPct` Meters.tsx:39-40, `faInt` BulkCreateDialog.tsx:50).
- **Raw enums never reach the user.** Excel label maps match the enum members exactly (excel.py:73-80, 227-233, 269, 272-278 vs models/enums.py — compared member-by-member; `_STATUS_LABELS` and the PDF stage labels are locked by tests/test_audit_category_one.py:168-180); PDF comment stages translate at render time with the raw value only as last resort (pdf.py:104-108, template:227); frontend has exhaustive `Record<Enum,string>` label maps (types.ts:11,42,341,514,627,790) and every badge/table routes through them; `recommendation` is stored Persian text from scheme thresholds (scoring_scheme.py:46-51), printed verbatim in the PDF; the remaining `.value` uses are dedup keys, audit data, metrics labels, and model-facing tool payloads — all data, not display.
- **No stray English reaches the user.** The only English `HTTPException` details sit behind the token-protected `/metrics` endpoint (main.py:224,229 — ops surface); the WeasyPrint-missing path returns a Persian 500 detail exactly as its comment promises (evaluations.py:1761-1769), and the archival sweep degrades to a logged skip + backfill (documents.py:41-67); Pydantic validation arrays are translated to Persian sentences with a field-label table (core/validation_errors.py).
- **RTL/physical-CSS sweep.** Root is `lang="fa" dir="rtl"` (index.html:2); logical utilities (ms/me/ps/pe/start/end) are used where flow-relative; I audited all 91 physical `left/right/pl/pr/ml/mr/text-left/right` sites: each icon↔padding and motion↔direction pair agrees for a fixed-RTL app (PasswordInput pl-11+left-2; SearchInput right-3+pr-9; toggle knob right-0.5↔right-[22px], direction locked by AdministrationPage.test.tsx:335; sidebar right / bell+profile dropdowns left-0 consistent with the sidebar side; slider marker `left: (5-n)/4` matches the RTL-flipped range input, ScoreForm.tsx:330,342; all LTR islands — usernames, emails, codes, verify URL, hash — are wrapped in `dir="ltr"`, often with `text-left`, which is intentional). No visual break found; the only residue is cosmetic (two search-input designs mirror their icon side).

## Could not check, and why
- **Visual rendering in a real browser** (no display/Playwright in this env): the RTL/CSS conclusions are code-audited pair-by-pair, not screenshot-verified.
- **Glyph shaping (joined forms) inside WeasyPrint/Pango output**: PDF bytes were produced and hash-verified in this environment (suite green; P03 re-verified sha256 live), and I verified per-codepoint cmap coverage — but I did not visually inspect shaped Arabic forms in a rendered PDF.
- **A deployment with `ORG_TIMEZONE ≠ Asia/Tehran`**: the frontend hard-codes `"Asia/Tehran"` (dates.ts:16) and test_org_timezone.py:136-137 deliberately fails if the two diverge; I did not stand up such a deployment (single-organization product; the lock is by design).
- **Copilot-generated Persian prose quality** (numerals/dates inside model answers): needs a real model key; the offline harness exists but live-model measurement was out of scope here (matches P04's "could not check").
