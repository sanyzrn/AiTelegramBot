P11 — Test quality review (the test suite itself) · NexaHR @ 27c83e5 · Mode: defects

## Verdict — 3 lines
The suite is behavior-first, not mock-first: 1542 backend tests contain zero assertions on mocks, wall-clock handling is disciplined, and both former defects the prompt names (`af_race_*` pollution, `employee_view_on` hiding a default-off module) are verified to be in a **fixed** state. The real blind spot is breadth, not depth: five mutations I executed — the org-unit rename cascade, the org-unit delete guard, both notification-preferences guards, the admin delivery-queue problem list, and the public QR-verify page's `valid` flag — **all survived** (plus one control mutation that was caught, validating the harness). Highest-value gap: nothing tests that renaming an org unit moves its personnel, and `org_unit` is a string key behind bulk cohorts, the HR-unit shield and per-unit analytics.

**1. Medium | backend/app/api/routers/org_units.py:138-144 | The rename→personnel cascade has no test — deleting it, the suite stays green (mutation MU-1 survived, 51 tests green).**
`update_org_unit` promises in its docstring that renaming a unit is a *correction* that moves the personnel rows whose `org_unit` string still carries the old name. That `db.query(Personnel)...update({...})` block is the only thing keeping personnel inside their unit after a rename. No test anywhere calls `PATCH /api/org-units/{id}` with `name`/`site` (grep over tests/: the only PATCH test is `test_hr_subject_chain.py:543-558` and it changes only `is_hr_unit`). Mutation: comment out the cascade → 51/51 green.
Reach: HR renames a unit in the admin panel (e.g. site added, or name typo fixed) → every member silently drops out of that unit on every string-keyed surface: bulk-create cohorts, the expiring-contracts watchlist, per-unit analytics — and, for an HR unit, the org-unit string that decides HR-unit membership (`tests/helpers.py:149-161` shows the string *is* the link). The audit event then reads `personnel_moved: 0` while HR believes the rename was complete.
Fix: one test that PATCHes a unit's name with two personnel rows in it and asserts both rows' `org_unit` followed, plus the audit event's `personnel_moved == 2`; and one test that a site-only change also moves rows.

**2. Low | backend/app/api/routers/org_units.py:158-197 | `DELETE /api/org-units/{id}` and its in-use guard are untested (MU-2 survived, 51 green).**
The endpoint refuses to delete a unit that has personnel (`if in_use:` at :178). Mutation: `if False and in_use:` → suite green; no test even mentions `DELETE` against `/api/org-units`.
Reach: a regression that drops the guard lets HR delete a unit with members; the catalog row disappears while `personnel.org_unit` strings keep referencing a unit that no longer exists in any form or list.
Fix: two tests — delete an empty unit → 204 and the row is gone; delete a unit with one member → 409 with the Persian count message and the unit still present.

**3. Low | backend/app/api/routers/notifications.py:82-131 | GET/PUT `/api/notifications/preferences` are untested — the address-required guards can be deleted with the suite green (MU-3 survived, 42 green).**
`update_preferences` is the only writer of `user.email`/`user.phone`, and its two 400 guards (:115-124) are what prevents a user from ticking "email/SMS" with an empty address — a tick that silently never delivers (the module-switch test's own docstring calls this shape "a tick with no effect"). Mutation: both guards → `if False and ...` → 42/42 green; grep: the word "preferences" appears in zero backend tests.
Reach: any authenticated user; PUT with `notify_by_email: true`, `email: ""` currently 400s — after the mutation it would persist the tick and the user waits for mail that never comes (the exact dead-queue shape `test_module_switches.py:252-291` warns about for the other half of the flow).
Fix: four tests — email-tick without address → 400; sms-tick without phone → 400; happy path persists address+flags and echoes `email_available`/`sms_available` from the configured channels; GET reflects them.

**4. Low | frontend/src/pages/VerifyPage.tsx:25-47 | The public QR-authenticity page has no test at all — making it declare every document valid passes the entire frontend suite (MU-6 survived, 407/407 green, full vitest run).**
