## Verdict — 3 lines
The concurrency core is unusually well-defended: every workflow/HW/me/plan write path reads its row `FOR UPDATE`, double-submit and double-confirm are backed by DB constraints or atomic conditional claims, the audit chain serializes on a transaction advisory lock, and the scheduler leader-lock is taken and released on a dedicated connection — all verified by execution (probes A/B below) plus the repo's own two-connection tests, no regressions of the ALREADY-FIXED list found. Three defects survive, all LOW and all in the periphery of the guarded core: `close_period` is the one period mutation that did not get the lock its own sibling `delete_period` documents as mandatory (a case can be born under a period that a concurrent close just shut — executed), `self_assessment.invite` is an unlocked read-decide-write on the record (executed), and the delivery sweep's send-before-commit boundary is at-least-once, contradicting the module's "دقیقاً یک‌بار" claim (UNVERIFIED, analysis only). Nothing above LOW; no finding touches the hashed legal document path.

## Findings — severity | file:line | what breaks | how to reach it | fix

**1. LOW | backend/app/api/routers/periods.py:247 (close body 238–292) + backend/app/api/routers/evaluations.py:452–454, stamped at :468 | A draft evaluation can be created under an evaluation period that a concurrent HR request just closed — exactly the state the close guard's 409 message refuses to create without `force`.** `close_period` loads via `_get_period_or_404` (periods.py:40–44, plain `db.get`, no `FOR UPDATE`) and counts open cases (:259–266) unlocked; `create_evaluation` reads the open period unlocked (:452–454) and stamps `period_id` at :468. No constraint, trigger or lock exists on this pair. — *How to reach:* HR closes the empty period "X" (`POST /api/periods/{id}/close`) at the same moment a unit supervisor opens a case (`POST /api/evaluations`); the supervisor's read of the open period lands before the close commits, the insert commits after it → an open draft lives under a closed period, is finalized under it later, and counts in `period_progress` of a closed period. *Executed:* probe C on `nexahr_p07` (session A reads period as `open`, session B closes+commits, session A inserts+commits) → record 2 persisted with `period_id` of a period now `closed`. The repo itself states the lock is required for this exact class of race in `delete_period`'s docstring (periods.py:184–191: "تا بینِ شمارش و حذف کسی پروندهٔ تازه‌ای روی همین دوره باز نکند") — close simply never got it. — *Fix:* `.with_for_update()` on the period row in `close_period` (mirror lines 192–194), and take the same row lock in `create_evaluation`/`bulk_evaluation.execute` (bulk_evaluation.py:242–244) before stamping `period_id`.

**2. LOW | backend/app/services/self_assessment.py:158 (read via `open_record_for`), :167 (stale check), :181–182 (write) | `invite` is a read-decide-write on the evaluation record with no row lock, so `self_assessment_invited_at`, an official audit event (`self_assessment_invited`) and a "فرم خودارزیابی این دوره برای شما باز است" notification can all land on a record whose self-assessment window is already closed.** The employee's own submit path is properly locked (`me.py:211` `for_update=True`) and HR's transition paths are locked, but invite reads through the unlocked `open_record_for` (:121–131) and writes without ever re-seeing the committed status. — *How to reach:* HR clicks "invite to self-assessment" while the supervisor's submit (`POST /api/evaluations/{id}/submit`) commits in between invite's read and write → the employee receives an invitation to a window that no longer exists; the record permanently carries `invited_at` for a phase that ended before it (HR's list then shows an invitation that can never be used). *Executed:* probe D on `nexahr_p07` — invite's read captured, a submit committed, invite's write completed → final state `status=submitted, self_assessment_invited_at=not null`. — *Fix:* load the record with `.with_for_update(of=EvaluationRecord)` in the invite path (same pattern as `me._my_record_or_404(for_update=True)`), so the status check at :167 is taken under the lock.

**3. LOW, UNVERIFIED | backend/app/services/delivery.py:160–197 with commit only at backend/app/services/scheduled.py:583 | The outbound queue is send-before-commit: `channel.send()` executes mid-transaction while the `sent`/`failed`/`abandoned` status writes only persist at the single `db.commit()` that ends `run_all_sweeps`.** A crash (or commit failure) after one or more successful sends but before :583 rolls the status rows back to `pending` → the next sweep re-sends the same SMS/email to the same recipients. — *How to reach:* process kill (deploy restart, OOM) or a DB error at commit during a delivery sweep that already sent a batch (default batch 50, `delivery_batch_size`, config.py:195). Not executed — proving it needs fault injection at the commit line, which I did not attempt; the interleaving is read directly from the code (no intermediate commit exists between `channel.send` at delivery.py:163 and scheduled.py:583). — *Fix:* commit each delivery row's outcome in a short transaction immediately after its send (`db.commit()` inside the loop, the session is otherwise idle), or invert to send-after-commit with a `sending` marker; at minimum, correct the "اجرای «دقیقاً یک‌بار»" claim in scheduler_lock.py:1 — the delivery leg is at-least-once by construction.

- **Double-submit (two parallel case creations).** Pre-check + partial unique index `uq_open_evaluation_per_personnel` + `IntegrityError` → 409 with the winner's id (evaluations.py:434–496); the bulk path adds per-row savepoints and reports `blocked_conflict` honestly (bulk_evaluation.py:283–297).
- **Double-confirm (copilot).** `_claim_for_execution` is an atomic conditional `UPDATE … WHERE status='pending'` committed immediately, before any tool runs (ai/confirmations.py:53–61, :108) — a parallel confirm gets 409 even mid-execution; failure paths roll back partial writes then record `failed` + audit (confirmations.py:124–158). Covered by tests/test_audit_fixes.py:578, :419, :456.
- **Session rotation.** `rotate_session` reads `FOR UPDATE OF AuthSession` with `populate_existing` (sessions.py:103–108); reuse outside the 60 s grace revokes the whole family (sessions.py:120–125) — the two-tab refresh case stays inside grace by design.
- **Lockout counters.** `record_failure` is upsert (`on_conflict_do_update` with a no-op SET) + `FOR UPDATE` + `populate_existing` (login_guard.py:76–93) — no lost counts toward the lockout, no `UniqueViolation` on the first concurrent insert; failure counting, audit and HR notification commit in one transaction (auth.py:132–149). - **Audit chain.** The only `AuditLog(` construction in the app is inside `log_event`, which takes `pg_advisory_xact_lock` before reading the previous hash (audit.py:87–109), so the chain cannot fork; UPDATE/DELETE are blocked by the DB trigger (audit.py:13, migration e8f4b127d905). **Executed (probe A):** 8 threads × 25 `log_event` on independent connections → `verify_chain` `ok=True, checked=200`. - **Scheduler double-run safety.** `run_sweeps_once` holds `pg_try_advisory_lock` on a *dedicated* connection for the whole sweep and unlocks on that same connection (scheduler_lock.py:57–98 — the M-10 fix holds, also under the mid-run commits that `run_all_sweeps` performs); losers record `skipped_locked`; a failing sweep rolls work back but still records a `failed` run (:80–91). Tests test_scheduler_reliability.py:135, :167, :206 and test_audit_fixes.py:741 (lock does not leak across mid-run commits) all pass.
