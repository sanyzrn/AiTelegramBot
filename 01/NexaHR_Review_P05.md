# P05 — Privacy & disclosure review (NexaHR @ 27c83e5)

## Verdict — 3 lines
Privacy core is genuinely well-built: every `suppressed_avg` call site counts *people* and applies the threshold, the HR-panel shield is enforced on list/detail/every write path, self-assessments are HR-only, audit payloads are capability-gated, and no employee-facing route reads another person's data. The one real hole is that the shield is enforced as per-endpoint discipline, not as a central rule — so the dashboard "in-progress" window and the self-assessment invite still see/write the shielded open case of an HR-unit member (all executed live). Three smaller parity defects (copilot HR queue vs UI list, copilot context people-scope, existence leaks on secondary surfaces) round out the list; nothing on the ALREADY FIXED list regressed.

## Findings — severity | file:line | what breaks | how to reach it | fix

**1. MEDIUM — dashboard.py:575-612 (`personnel_in_progress`) — the only HR-panel window with no shield and no own-case guard.**
What breaks: the endpoint returns an *open* record (`IS_OPEN_RECORD`, line 589) filtered only by `_can_view_personnel` (line 583), which is `True` for every HR user (sees_all_personnel) — so HR reads the shielded in-flight case of an HR-unit colleague: `evaluation_id`, `evaluation_code`, exact `status`, `was_returned` (queried from AuditLog, line 595-605) and `created_at`. Every other surface refuses this exact record: the list filters `~IS_SHIELDED_FROM_HR_PANEL` + own case (evaluations.py:637-640), detail raises 403 via `ensure_hr_may_handle` (evaluations.py:190, self_evaluation.py:218-229), and all HR writes sit behind the same guard. Polled repeatedly, the endpoint is a live tracker of a teammate's chain progress. Cross-check: `radar`/`trend` (524-568) share the guard but are finalized-only, so the shield (open-only by definition, workflow.py:151/154) correctly does not apply to them.
How to reach (executed): role=hr viewer; subject in an `is_hr_unit` org unit with an open `hr_review_skipped=True` case → `GET /api/evaluations` hides it, `GET /api/evaluations/{id}` → 403, but `GET /api/dashboard/personnel/{id}/in-progress` → 200 `{evaluation_id: 1, evaluation_code: "EVL-9001", status: "draft", was_returned: false}`. An HR user also sees their *own* open case here (no own-case exclusion, contrast evaluations.py:640).
Fix: after the `_can_view_personnel` check add `ensure_hr_may_handle(record, current_user)` (import from `services/self_evaluation.py`) — it returns silently for non-HR roles, so employees/supervisors keep their path; shielded and own cases then read `null` like everywhere else.

**2. LOW — shielded-case existence/state leaks + an HR write on the shielded case (three surfaces, one root: "open record" checks that ignore `IS_SHIELDED_FROM_HR_PANEL`).**
What breaks: the shield's promise ("تا پیش از ثبت نهایی از پنل منابع انسانی قابل دسترسی نیست", self_evaluation.py:226-228) is broken by:
- personnel.py:230-247 (`_with_accounts`): `open_evaluation_id` + `self_assessment_state` on every personnel row — `state=pending/invited` additionally reveals the case is still in `draft`; `open_evaluation_id` is the shielded record's id.
- dashboard.py:487-494 (`expiring_contracts`): `has_open_evaluation=True` for a shielded subject — HR's contract screen discloses that the colleague has an open case.
- personnel.py:282-303 (`invite_to_self_assessment`) + services/self_assessment.py:146-204 (`invite`): no shield check — HR *writes* `self_assessment_invited_at` onto the shielded record (an out-of-chain HR effect, exactly the class the shield exists to block per workflow.py:137-141) and the response echoes the shielded record's `open_evaluation_id`; the copilot twin `invite_self_assessment` (ai/tools/evaluations.py:479-499) additionally returns the case's `evaluation_code` in its payload. Same pattern again in ai/tools/people.py:120-150 (`_person_payload` → `open_evaluation_id`), code-verified.
How to reach (executed): HR viewer; HR-unit member with active account and open shielded case → `GET /api/personnel` shows `open_evaluation_id=1, self_assessment_state="pending"`; `GET /api/dashboard/expiring-contracts` shows `has_open_evaluation=true`; `POST /api/personnel/{id}/invite-self-assessment` → 200 with `open_evaluation_id=1` and the record's `self_assessment_invited_at` set in DB.
Fix: add `~IS_SHIELDED_FROM_HR_PANEL` to the open-record subqueries in `_with_accounts` (personnel.py:236-243), `expiring_contracts` (dashboard.py:487-493) and `_person_payload` (tools/people.py:120-124), and raise the same 403 wording as `ensure_hr_may_handle` in `self_assessment.invite` when `hr_panel_is_shielded(record)`.

**3. LOW — ai/tools/evaluations.py:530-532 (`my_open_cases`, HR branch) — queue drifts from the UI list: no own-case exclusion, no shield filter.**
What breaks: the branch is `status == submitted` only, while the UI queue for the same role is `submitted AND ~IS_SHIELDED_FROM_HR_PANEL AND subject != user.personnel_id` (evaluations.py:625-640); the comment claims "همان چیزی که فهرست رابط هم نشان می‌دهد". Shielded cases cannot reach `submitted` (all five transitions into `submitted` guard on `not skips_hr_review`, workflow.py:179-297 — code-verified), so the reachable defect is the HR user's *own* case: an hr-role account whose `personnel_id` sits outside the HR unit has a normal case that the UI queue hides but the copilot queue shows (code + status + subject name via `_describe_record`), and the UI's own rationale (evaluations.py:626-634) is that the queue is the window to evidence the subject must not read pre-announcement.
How to reach (executed): hr-role user linked to non-HR-unit personnel, own case `submitted` → `my_open_cases` count=1 with the own case present; `GET /api/evaluations` for the same user → own case absent.
Fix: in the HR branch add `& ~IS_SHIELDED_FROM_HR_PANEL` and `& (EvaluationRecord.subject_personnel_id != ctx.user.personnel_id)` (or route the branch through `scope_evaluations_for_role`). Sibling drift already reported for the CEO branch (`deputy_approved` only vs `IS_ON_CEO_DESK`) — queue completeness, not a leak (P02#3).

**4. LOW — ai/context.py:42-67 (`_visible_personnel_ids`) — missing the record-seat union its twin got, so the model text under-reports the user's real scope.**
What breaks: the twin in ai/tools/people.py:46-82 unions `EvaluationRecord` seats (71-79) on top of `EvaluationAccess` rows; `context.py` unions only the access rows (57-63) + own id. A holder of a record seat whose access row names someone else — legal via `may_act_at` over-rank or after a chain change — is allowed by `_can_view_personnel` (personnel.py:118-149, record-seat clause) and visible to `search_personnel`, but absent from the copilot context people block and from the "پرسنل در دامنهٔ دید شما" count (context.py:107-123, 169-179). Same question, two answers — the exact parity class this repo keeps re-breaking; the evaluations block of the same file *does* use the real `scope_evaluations_for_role` (context.py:134-148), so the file disagrees with itself too.
How to reach (executed): deputy-role user seated in `unit_supervisor_user_id` of a record whose access row lists another supervisor → `_can_view_personnel=True`, person in tools ids, person NOT in context ids (DRIFT=True).
Fix: have `context._visible_personnel_ids` call the people-tools implementation (or move it to `services/authorization.py` next to `sees_all_personnel`); extend `tests/test_ai_people_parity.py` to lock the context copy as well.

## Proposals — max 6, ranked
1. **One policy for "does this HR-unit colleague have a case in flight?"** Today HR gets *contradictory* answers on one screen: list/detail say nothing, in-progress/personnel-list/expiring-contracts say "yes, here's the id and stage", invite says "I'll write on it". Outcome for HR: the shield becomes a single understandable rule ("در جریانِ هم‌تیمی‌ام را نمی‌بینم — نهایی‌شده را می‌بینم") instead of four endpoints disagreeing. Change: apply `~IS_SHIELDED_FROM_HR_PANEL` + own-case exclusion at the four sites in Findings 1-2 (dashboard.py:583-592, personnel.py:236-243, dashboard.py:487-494, self_assessment.invite). Cost: 4 files + 2 test files. Breaks: nothing functional; the self-assessment invite button disappears for HR-unit members (deliberate — deputy/CEO can invite from their own path if ever needed).
2. **Copilot queue reads the same allowlist as the UI queue.** Outcome: HR never hears "پرونده‌ای روی میز شماست" from the assistant about a case the panel refuses to open. Change: HR branch of `my_open_cases` reuses the two where-clauses of `scope_evaluations_for_role` instead of hand-rolled `status == submitted`. Cost: 1 file (ai/tools/evaluations.py) + the parity test. Breaks: nothing; employee/CEO branches untouched.
3. **Unify `_visible_personnel_ids` in one place.** Outcome: a supervisor seated on a record by over-rank gets the same copilot context as their pages — no more "I can open him but my assistant doesn't know him". Change: move the people-tools implementation (with the record-seat union) to `services/authorization.py` and have `context.py` import it. Cost: 2 files + parity test. Breaks: nothing — it only widens the under-scoped context copy to match real access.
4. **Replace the accidental shield leaks with one deliberate aggregate.** HR legitimately needs capacity planning, not case files: a single card "N پروندهٔ بازِ واحد منابع انسانی — رسیدگی با معاونت/مدیرعامل" on the HR dashboard would satisfy the need the leaked flags currently (accidentally) serve, without naming anyone. Change: one count query with `IS_SHIELDED_FROM_HR_PANEL` in `dashboard.overview` + one schema field. Cost: 2 files. Breaks: nothing.
5. **Production guard for `NOTIFICATION_CHANNEL_CONSOLE`.** One wrong env var in production pipes employee names, case codes and recipient addresses into server logs forever. Outcome: impossible to misconfigure silently, same as the existing four `_forbid_*` production validators. Change: a `model_validator` rejecting `notification_channel_console=true` when `environment == "production"`. Cost: 2 files (config.py + a test). Breaks: any staging box that runs production-mode with the console channel — it must wire SMTP/SMS, which is the intent.
