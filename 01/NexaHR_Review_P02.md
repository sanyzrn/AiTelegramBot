## Findings — severity | file:line | what breaks | how to reach it | fix

**1. Medium — `backend/app/api/routers/evaluations.py:641-646` (`scope_evaluations_for_role`) vs `backend/app/api/routers/evaluation_access.py:43-47`**
- What breaks: the evaluations list binds each chain role to exactly one seat field (`unit_supervisor` → `unit_supervisor_user_id == user.id`, `deputy` → `deputy_user_id == user.id`, `ceo` → `ceo_user_id == user.id`), while seat *creation* deliberately admits higher-rank users into lower seats via `may_act_at`. A user seated in a seat that outranks his role cannot see the open case he is legally required to act on — in `/api/evaluations` (list), `export.xlsx` filters, and the copilot `search_evaluations`, which all reuse this function. The detail-page guard `_ensure_can_view` (evaluations.py:193) uses all three seats (`allowed_ids`), so the two guards disagree: the case is openable by id but invisible in every list/queue.
- How to reach it (executed, VERIFIED): HR sets `unit_supervisor_user_id = <deputy-role user>` for a personnel (allowed: `may_act_at(deputy, unit_supervisor)` is True at evaluation_access.py:43), deputy calls `POST /api/evaluations` (create guard passes: he is the scorer seat), scores it. Running the real `scope_evaluations_for_role(select(EvaluationRecord), CurrentUser(role=deputy, …), db)` against that DB state returns `[]` — his own pending case never appears in his list; dashboard queue, export and copilot search ditto. Same blindness for a CEO seated in the unit_supervisor seat with a different CEO in the ceo seat (a legal, non-redundant shape), waiting at `hr_approved`.
- Fix: for the three chain roles, scope by *seats* like the detail guard already does — `or_(unit_supervisor_user_id == user.id, deputy_user_id == user.id, ceo_user_id == user.id)` — or at minimum add the over-rank seats per role. Seat-based, so it opens nothing to non-seat-holders (same allowlist semantics as `_ensure_can_view`).

**2. Low/Medium — `backend/app/services/notifications.py:389-505` (`notify_for_workflow_action`); transitions at `backend/app/services/workflow.py:427` and `:442`; dispatched from `backend/app/api/routers/evaluations.py:1170` and `:1190`**
- What breaks: the notification switch has no branch for `ceo_return_no_deputy` and `ceo_return_no_deputy_hr_subject` — the only two of the nine return actions (and 22 transitions overall) that produce **zero** notifications in every chain shape. When the CEO returns a no-deputy-chain record (`hr_approved → submitted`), the HR queue is told nothing (compare `deputy_return`/`ceo_return_manager`, which notify `_hr_queue_ids`); in the HR-subject variant (`hr_approved → draft`), the unit supervisor who must re-score is told nothing (compare `ceo_return_ceo_only`/`ceo_return_manager_hr_subject`, which notify `_tell_the_scorer`). The case silently reappears in the HR queue or the scorer's draft; only the `was_returned` flag and, days later, the SLA sweep reveal it.
- How to reach it (executed, VERIFIED): no-deputy chain (supervisor + CEO, no deputy, HR review on): submit → hr-approve → CEO `POST /api/evaluations/{id}/return {"reason": …}` → 200, status `submitted`; calling the real `notify_for_workflow_action(db, record, "ceo_return_no_deputy")` creates 0 notification rows (matrix executed over all 8 shapes; every sibling return action notifies its owner). Same for `ceo_return_no_deputy_hr_subject` (0 rows; correct recipient would be the scorer).
- Fix: add two branches — `ceo_return_no_deputy → _hr_queue_ids(db, record)` and `ceo_return_no_deputy_hr_subject → _tell_the_scorer(record, evaluator_id)` — and add a parity test that locks every key of `TRANSITIONS` to a notification branch, so the next return transition cannot ship silently.

**3. Low — `backend/app/services/ai/tools/evaluations.py:549-551` (`my_open_cases`, CEO branch)**
- What breaks: the copilot's "my open cases" for the CEO tests only `status == deputy_approved`, but the CEO's desk legally also holds `hr_approved` when the deputy seat is empty (no-deputy chain, incl. its HR-subject variant) — exactly what `IS_ON_CEO_DESK` (`workflow.py:166-169`) and the UI queue (`?on_ceo_desk=true`, fixed and tested in `test_no_deputy_chain.py:200`) already include. The CEO who asks the assistant sees no waiting case that the UI shows; the two views disagree, in the direction of "nothing needs me".
- How to reach it: no-deputy chain, record at `hr_approved`; CEO opens the copilot and asks for his open cases → the tool's CEO branch condition excludes it (deterministic condition; VERIFIED by reading — the branch is a two-line WHERE with no other source of rows).
- Fix: build the branch from `workflow.IS_ON_CEO_DESK` (`& (ceo_user_id == ctx.user.id)`) instead of the bare status equality.

**4. Low — `backend/app/api/routers/evaluations.py:1661-1665` (`reassign_stage_owner`) vs `backend/app/api/routers/evaluation_access.py:43-47`**
- What breaks: reassignment demands an *exact* role match (`new_user.role != expected_role → 400`), while seat creation deliberately allows over-rank seats (`may_act_at`). A vacated seat that was legally held by a higher-rank user (CEO in the unit_supervisor seat — the shape `single_decider` documents and the DB explicitly permits; deputy in the supervisor seat likewise) cannot be given back to the same over-rank role: the rescue tool that the "seats vacated" notification explicitly tells HR to use (`notifications.py:310-313`) rejects the natural replacement. HR falls back to an exact-role user, or, in an org with no active unit_supervisor account, to cancellation only.
- How to reach it: create a chain with the CEO as unit_supervisor seat holder (allowed at access creation), the holder leaves the organization (`_close_out_departure` cancels only the departed person's *own* case and notifies HR about their seats in others' cases), HR calls `POST /api/evaluations/{id}/reassign` with `stage_field="unit_supervisor_user_id"` and `new_user_id=<any ceo- or deputy-role user>` → 400 «باید نقش «مسئول واحد» داشته باشد».
- Fix: replace the equality check with `may_act_at(new_user.role, expected_role)` (mirroring access creation), keeping the subject and redundant-pair guards unchanged.
