# P03 — Scoring & legal PDF (compute_result, per-indicator weights, absent-section redistribution, scheme versioning & mid-cycle activation, bonus rules, snapshot.py, documents.py, pdf.py, hash + QR verify)

## Verdict — 3 lines
The score engine and the signed-document pipeline are sound where it is easy to be wrong: redistribution, weighted schemes, threshold bands, bonus clamping, scheme stamping/mid-cycle activation, copilot delegation, signatories, and the hash→QR→verify chain were all exercised live on a scratch DB and behave correctly, with no regression of any ALREADY FIXED item. Three LOW defects remain, all of the "the printed page is not quite what the screen said" class: the legal PDF's row order is unspecified (plan-dependent — demonstrated live: the same finalized data yields two different document orders under two query plans), the frontend bonus preview can disagree with the document by 0.01 on a 3-decimal input, and the read API still shows only the raw bonus while the document prints the clamped one (the repo's own open item, re-verified reproducing today).

## Findings — severity | file:line | what breaks | how to reach it | fix

**1. LOW | `backend/app/services/snapshot.py:63-68` and `:71-75` (consumers `:146-156`, `:157-164`; template `backend/app/templates/evaluation_summary.html:143`, `:162`, `:226`) | The row order of the legal PDF is unspecified — none of the three snapshot selects has an `ORDER BY`, so the order frozen into the hashed document is whatever query plan the finalize connection happens to get.** `build_final_snapshot` loads `EvaluationScore` and `EvaluationComment` with bare `select(...).where(...)` and no ordering; the template then prints `snapshot.scores` into the «شاخص‌های عمومی / تخصصی» tables and `snapshot.comments` into «کامنت‌های مراحل بررسی» in exactly that order. *Executed, not reasoned:* on a scratch DB I finalized a 20-indicator record whose scores were PUT in reversed display order, then called `build_final_snapshot` twice on the identical finalized row — under the default plan the scores come out `[1,2,3,…,20]` (a plan using `uq_evaluation_scores_record_indicator` returns indicator order), with `enable_indexscan/bitmapscan/indexonlyscan=off` (seq scan) they come out `[1,13,20,19,18,…]` — i.e. exactly the raw payload order of the PUT, confirmed as the physical heap order via `ctid` (`(0,1)→ind 1, (0,2)→ind 13, (0,3)→ind 20…`). Worse, every draft auto-save PUT rewrites *every* scored row (`_replace_scores` upserts the full payload with `on_conflict_do_update`, `evaluations.py:345-355`), so heap order equals the *last save's* payload order — any API client controls it, and even the UI's own edit sequence reshuffles it. Whichever order the finalize-time connection's plan produces is frozen into `final_snapshot` and printed on the signed document; two records with identical inputs can print in different orders, and a record can print its indicator rows in an order that matches neither the form (`section, display_order` — `indicators.py:74`) nor the id order. How to reach: any scorer (or direct API integration, e.g. the copilot's `create_evaluation` + a custom client) PUTs `/scores` with rows in a non-display order or edits a score via auto-save → chain finalizes under a heap-order plan → the PDF's evidence tables are permuted relative to the form the evaluator saw. Comment order is the same defect (`:66-68`) but in practice both natural plans return heap = chronological order here (verified live), so the scores tables are the exposed half. No number changes — but this is the signed document's evidence column, and its order is currently an accident of query planning. Fix: in `build_final_snapshot`, order scores by the record's own framework indicator order — join `Indicator` and `order_by(Indicator.section, Indicator.display_order, Indicator.id)`, the same source the form uses — and comments by `(EvaluationComment.created_at, EvaluationComment.id)`; note the codebase already treats this order as intended (`EvaluationComment.comments` relationship declares `order_by="EvaluationComment.created_at"` at `models/evaluation.py:210-214`, and `_persisted_scores` orders by id at `evaluations.py:298-302`) — the snapshot's raw selects are the only readers that bypass it. New snapshots only; archived PDFs stay byte-frozen by design.

**2. LOW | `frontend/src/components/ScoreForm.tsx:213` (render `frontend/src/pages/EvaluationDetailPage.tsx:922-925` and `:1133-1139`; backend twins `backend/app/services/evaluation.py:241` + `Numeric(4,2)` at `backend/app/models/evaluation.py:133`, accepted raw at `backend/app/schemas/evaluation.py:235`) | The «+ Y امتیاز ویژه» preview can differ from the signed document by 0.01 — the `appliedBonus` twin still rounds half-up on the double while the server pipeline rounds the stored decimal half-away-from-zero.** `appliedBonus` computes `Math.round(capped * 100) / 100` on the *typed* value; the server stores the typed value into `bonus_points Numeric(4,2)` — PostgreSQL rounds it half-away-from-zero — and `applied_bonus`/the document then use the stored value. Concrete path (both halves executed): evaluator types bonus `1.005` (schema accepts any float ≥0; PATCH returned 200 and read back `1.01`) → the form's preview computes `Math.round(100.49999999999999)/100 = 1.00` and shows «+۱» beside the ring (the ring's 1-decimal total still agrees), while the finalized document prints «امتیاز ویژه +۱٫۰۱». This is the remaining sibling of the `round1` fix the repo already shipped (`utils/rounding.ts` implements Python-compatible decimal expansion for the *base* percentage; `appliedBonus` was missed). Two corrections to the naive framing of this bug: (a) the `2.675` example *agrees* — `2.675*100 === 267.5` exactly in IEEE, so both sides give 2.68; divergence needs a value whose double product lands below the tie (e.g. `1.005`, `0.145`→`0.14` vs PG `0.15`); (b) Python's banker's `round(...,2)` at `evaluation.py:241` is not the diverging step — at finalize it only ever receives the already-2-decimal DB value. Reach: any evaluator who types a 3-decimal bonus (free-text input, no step constraint client- or server-side) with base ≤ 97-ish so the clamp doesn't already cut the third decimal. Fix: quantize the raw to 2 decimals in one place — either a `round2` built like `round1` (decimal expansion, tie-to-even won't match PG's half-up, so prefer…) — or, simpler and airtight, round the typed bonus to 2 decimals *in the form before preview and submit* (`Math.round(v*100)/100` on the *string*-parsed decimal, or a step=0.01 input) and reject >2-decimal values server-side in `SpecialScoreUpdate`, so preview, DB, and document always compute on the same number.

**3. LOW | `backend/app/schemas/evaluation.py:154` (consumer `frontend/src/pages/EvaluationDetailPage.tsx:769`) | The read API exposes only the *raw* bonus, so the subject's file page shows a number the signed document does not.** `EvaluationRead.bonus_points` is the raw column value (deliberately raw in the DB); the applied value exists only inside the snapshot (`snapshot.py:140` via `applied_bonus_for_document`) and the Excel (`evaluations.py:804-808`). *Executed live:* a record with base 98.0 and raw bonus 5 finalized with applied 2.0 and final 100.0 — `GET /api/evaluations/{id}` reports `bonus_points: 5.0` while the rendered document prints «امتیاز فرم ۹۸٪ + امتیاز ویژه +۲ = امتیاز نهایی ۱۰۰٪». The file page (`ReadOnlyScoring`) shows «امتیاز ویژه: ۵ امتیاز» for the paper that says +۲. This is a fresh-evidence confirmation of the repo's own open item (`docs/open-findings.md`, «سندِ رسمی و محاسبه» → «خطِ "+ ۵ امتیاز ویژه" در صفحهٔ پرونده clamp نمی‌شود»); it is not on the prompt's ALREADY FIXED list — the fixed piece was the *form-side* line beside the ring (CHANGELOG «۹۸ + ۵ = ۱۰۰»), the read-side display is the part still open — so it is not a regression. Reach: any record where `100 − base_pct < raw ≤ bonus_max_points` (perfect scores plus any bonus, or a high base under a small cap) → open the finalized detail page. Fix: add the applied value to the read schema (`applied_bonus_for_document(db, record)` already computes it, is used by the Excel path, and returns `None` when nothing was applied) and show it next to the raw in `ReadOnlyScoring`, the way the document and Excel already do.

## Verified correct
- **`compute_result` math, including absent-section redistribution** — executed directly: only-general and only-specialized frameworks both yield `base=100` for all-5 scoring; weighted scheme (indicator weights {1:3, 2:1}) gives exactly 84.0; the zero-weight-all-sections fallback (simple average) gives 100. Frontend `computePreview` (`ScoreForm.tsx:155-198`) mirrors it step for step — same weight map with string keys matching `AppConfig.indicator_weights`, same present-section renormalization, same fallback — and that fallback is unreachable through validated schemes anyway (`SchemeInput` forces section weights to sum to exactly 1 and indicator weights > 0; re-validated again at activation by `ensure_scheme_is_valid`).
- **Threshold table** — half-open `[lower, upper)` bands leave no gap and no double-label: executed labels at 0/59.99/60/74.99/75/89.99/90/99.99/100; a final of 100 gets the top band; `final_weighted_pct ≤ 100` structurally because the bonus cap sits on the addend (`100 − base`), verified by the clamp execution below.
- **Bonus clamping end-to-end** — executed: base 98 + raw 5 → applied 2.0; base 100 + raw 5 → 0.0; negative → 0.0; raw 7 → cap 5.0. The identity «امتیاز فرم + امتیاز ویژه = امتیاز نهایی» holds on the rendered document (98.0 + 2.0 = 100.0 verified in the generated HTML); the raw stays in `record.bonus_points` and in the `special_score_set` audit event; the applied value is what the snapshot (`snapshot.py:140`), the Excel (`excel.py:178-197` via the router's `applied_bonus_for_document` map), and the PDF print. Write-time `validate_bonus` independently rejects raw > scheme cap, negatives, and reason-less bonuses, backed by two DB CheckConstraints.
- **Scheme versioning and mid-cycle activation** — records stamp both `scoring_scheme_id` and `indicator_framework_id` at creation; `rules_for_record` reads the stamp (never `active_scheme`) and `finalize_scoring` uses it; schemes are immutable once active (no edit endpoint exists; `DELETE` refuses non-drafts); `activate()` enforces draft-only + creator≠activator + `ensure_scheme_is_valid` *inside the service*, so the copilot's `activate_scoring_scheme` (which calls the service directly) cannot bypass them; the detail payload carries the record's own stamped rules (`_to_detail` → `scoring_rules`) and the frontend prefers them over today's active config, so an open record is previewed and validated under its own version even after a mid-cycle activation.
- **Finalize guards on both paths** — the copilot's `advance_evaluation` delegates every action to the real endpoint functions with real payloads; `submit` runs `finalize_scoring`, and `hr_approve`/`ceo_finalize` pass a background-task queue that the tool drains so the PDF archives. There is deliberately no copilot tool for `upsert_scores`/`set_special_score` (verified against the full tool registry). `apply_transition` independently refuses a finalized transition without a result or snapshot, so a skipped `before` cannot close a record without a document.
- **Snapshot versioning** — v6 writer (`SNAPSHOT_VERSION = 6`); every reader tolerates older shapes by key presence, not version dispatch: the template's `{% if snapshot.signatories %}` else-branch rebuilds the ≤v4 block, `self_assessment` (v4+) and `bonus_points` (v2+) blocks are silently omitted when absent, `verify.py` reads only `personnel`. Archived v4 documents render as originally printed. (The module docstring's "render branches on version" is implemented as key-presence branching — the guarantee holds by a different mechanism than the comment implies.)
- **Signatories** — executed for the full chain: «مسئول واحد، منابع انسانی، معاونت، مدیرعامل» from the record's real seats, one row each, `single_decider` False; code-read plus the dedicated suites (`test_document_signatures.py`, `test_direct_ceo_hr_finalization.py`, `test_redundant_chain_seat.py`) cover the merged CEO-in-supervisor-seat row, the no-deputy shapes, and HR omission when `hr_review_skipped`.
- **Hash + QR verify path, exercised live** — `sha256(pdf_bytes) == document.sha256`; `GET /api/verify/{token}` returns 200 with the matching hash, final pct, code and recommendation; `GET /api/verify/{evaluation_code}` (sequential, guessable) returns 404; the token is `secrets.token_urlsafe(24)` stamped only at `ceo_finalize` (`evaluations.py:1057`) with a unique index; the rate limit uses one shared `30/minute` scope so per-token buckets cannot defeat guess-limiting; QR embeds `{public_base_url}/verify/{token}` matching the frontend route.
- **Document archival robustness** — archival is idempotent with an `IntegrityError` race handled inside a SAVEPOINT; render failures never fail finalization; the scheduler sweep backfills finalized-with-snapshot records lacking documents and deliberately skips snapshot-less ones; `/summary.pdf` distinguishes not-finalized (400) from WeasyPrint-missing (explicit 500).
- **PDF hardening & fonts** — the templates-only URL fetcher blocks external and `file://` sources, Jinja autoescape is on (evaluator text cannot inject markup into the signed document), all four woff2 files including `Vazirmatn Latin` exist under `app/templates/fonts/`, and Jalali dates render through `clock.to_local` (Asia/Tehran), not the UTC wall clock.
- **Regression sweep of the ALREADY FIXED items in this angle** — applied (not raw) bonus in document/Excel (verified live), signatories from real seats (verified live), `single_decider` recognises CEO-direct (test + code read), Vazirmatn Latin fonts (files + declarations verified), `core/clock.py` day boundaries (code read: `to_jalali` → `to_local`), `add_comment` calling `ensure_hr_may_handle` and the stage/owner table (code read; the stage guard also fired live — a draft-stage comment attempt got a 403 with the correct Persian message). None is broken.
